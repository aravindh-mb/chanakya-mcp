Caveats and known issues

  • Wrong answer On the sample monorepo, get_callers misses service.create_user() and get_dependents misses the 8 files importing @sample/shared. Those two rows look cheap partly because the answers are incomplete. Not fixed yet.
  • The grep baseline on VS Code is unrealistically expensive (a plain grep for createDecorator returns ~400k tokens). Claude Code caps grep output, so a realistic agent lookup there is closer to ~8,000 tokens, which puts the realistic saving at about 75–99% per lookup, not 98.5%.
  • File structure answers are the weakest case: get_file_structure on textModel.ts returned 19,228 tokens versus 27,942 for reading the file (31% saved).
  • Peak memory on VS Code is still about 2.9 GB (4 parser workers plus building the indexes at the end). Normal projects measured about 1–1.5 GB.
  • Not measured: a real Claude or Gemini session end to end. Gemini CLI was not installed on the test machine.

What changed

  • Search index: a COLLATE NOCASE name index for the default case-insensitive search; case-sensitive prefix search now uses a range the index can seek.
  • Text search: reads 32 files at a time and skips files whose content cannot contain the query.
  • Graph linking: starts from import bindings and reads a page at a time instead of loading every unresolved reference into memory; the join order is pinned so SQLite does not pick a slow plan.
  • Parallel parsing: up to 4 worker threads, with the next batch parsing while the previous one is written; identical results to single-threaded mode.
  • Bulk first index: an empty database builds its secondary indexes once at the end instead of on every row.

Reproduce: pnpm run bench:sample (sample monorepo) and pnpm run bench (this repository). The VS Code numbers came from a one-off script run against a shallow clone.
